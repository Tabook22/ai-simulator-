Understand the problem and the data

A neural network project starts with a sentence, not a library. Write down what goes in, what comes out, and how you will know whether the answer is useful.

House-Price case

Question: predict a house price from its area and number of bedrooms.

Inputs: area (m²), bedrooms.

Target: actual price in OMR.

Exam-Score case

Question: predict an exam score from study hours and attendance.

Inputs: study hours/week, attendance %.

Target: actual score out of 100.

The four exam rows

StudentStudy hours/weekAttendanceExam score
1570%58
21085%75
31595%89
4880%68
The target is not an input. Never feed the actual score or price into the network. It is used only after a prediction to measure the error. If the answer is an input, the model has nothing to learn.

What you are really building

  1. Data contract: two numeric features, one target, and a clear split.
  2. Model: a small network that maps the two features to one number.
  3. Training loop: predict, measure the loss, backpropagate, update.
  4. Evaluation: separate validation and test data, reported honestly.
  5. Interface: a way for a person to explore the data and the model.
Checkpoint 1: Explain in one sentence why the target cannot be an input.

Build the data pipeline

Split first, then scale. Fit the scaler on the training rows only, and reuse the same mean and standard deviation for validation and test.

FEATURES = ["study_hours", "attendance"]
TARGET = "exam_score"

train = frame[frame.split == "train"].reset_index(drop=True)
validation = frame[frame.split == "validation"].reset_index(drop=True)
test = frame[frame.split == "test"].reset_index(drop=True)

mean = train[FEATURES].to_numpy(float).mean(axis=0)
std = train[FEATURES].to_numpy(float).std(axis=0, ddof=0)
std[std == 0] = 1.0

def scale(rows):
    return (rows[FEATURES].to_numpy(float) - mean) / std

x_train = scale(train)
x_validation = scale(validation)
x_test = scale(test)

Why scaling matters

Study hours are roughly 1–20; attendance is 50–100. Without scaling, attendance would dominate the products and gradients only because its numbers are larger — not because it is more useful.

Scale the target too

y_raw = train[TARGET].to_numpy(float)
y_mean = y_raw.mean()
y_std = y_raw.std(ddof=0) or 1.0
y_train = ((y_raw - y_mean) / y_std).reshape(-1, 1)
Leakage check: never compute mean or std on the full dataset. Validation and test must look like unseen data.
Checkpoint 4: You can explain why the scaler is fitted on training data only.

Design the network

The network is deliberately small so every number can be traced:

Inputs2 features
→
Hidden3 neurons · ReLU
→
Output1 number · Linear

Count the parameters

LayerWeightsBiases
Input → hidden2 × 3 = 63
Hidden → output3 × 1 = 31
Total94

The count depends on the architecture, not on the number of students:

2 features → 2 input nodes · 1,000 rows → still 2 input nodes.

Initialize with seed 42

import numpy as np
rng = np.random.default_rng(42)
w1 = rng.normal(0.0, np.sqrt(2.0 / 2.0), (2, 3))
b1 = np.zeros(3)
w2 = rng.normal(0.0, np.sqrt(2.0 / (3.0 + 1.0)), (3, 1))
b2 = np.zeros(1)

Seed 42 makes the starting point reproducible. The same seed, the same code, and the same architecture give the same initial network.

Train in mini-batches

One batch means: predict 100 rows, average the errors, calculate the gradients, and update once.

def forward(x, w1, b1, w2, b2):
    z1 = x @ w1 + b1
    hidden = np.maximum(0.0, z1)       # ReLU
    prediction = hidden @ w2 + b2     # Linear
    return z1, hidden, prediction

order_rng = np.random.default_rng(43)
for epoch in range(1, 11):
    order = order_rng.permutation(len(train))
    for start in range(0, len(train), 100):
        batch = order[start:start + 100]
        z1, hidden, prediction = forward(x_train[batch], w1, b1, w2, b2)
        dpred = 2.0 * (prediction - y_train[batch]) / len(batch)
        dw2 = hidden.T @ dpred
        db2 = dpred.sum(axis=0)
        dhidden = dpred @ w2.T
        dz1 = dhidden * (z1 > 0)
        dw1 = x_train[batch].T @ dz1
        db1 = dz1.sum(axis=0)
        w1 -= 0.05 * dw1
        b1 -= 0.05 * db1
        w2 -= 0.05 * dw2
        b2 -= 0.05 * db2

The shape of one batch

100 students × 2 features = 200 input values
200 input values → 100 predictions
100 errors → 1 average batch loss
1 loss → gradients → 1 update of all 13 parameters

What happens across an epoch

  1. Batch 1 uses the initial weights; it updates once.
  2. Batch 2 starts from batch 1’s updated weights.
  3. … through batch 10.
  4. Ten batches = ten updates = one epoch.
  5. Shuffle and repeat for the next epoch; do not reinitialize.
100 or 1,000 students? More rows change the amount of evidence, not the number of parameters. The 2 → 3 → 1 network still has 9 weights and 4 biases.
Checkpoint 6: After 10 epochs, the updates counter reads 100.

Evaluate honestly

Training loss tells you how well the network fits what it has seen. Validation tells you whether a settings choice generalizes. Test is opened once, at the end.

def predict(x):
    _, _, scaled = forward(x, w1, b1, w2, b2)
    return np.clip(scaled.reshape(-1) * y_std + y_mean, 0.0, 100.0)

def mae(x, actual):
    return float(np.mean(np.abs(predict(x) - actual)))

print("train", mae(x_train, y_train_score))
print("validation", mae(x_validation, y_validation_score))
print("test", mae(x_test, y_test_score))

Use more than one number

MetricQuestion it answers
MAEOn average, how many points or OMR are we off?
RMSEHow large are the larger mistakes?
BaselineWhat would predicting the training mean give?

Design the application architecture

A model in a script is not yet an application. The downloadable Neuron Lab app separates four jobs:

Excel / data1,200 rows
→
FastAPItrain · validate · predict
→
React UIsteps · lab · charts

Backend

Owns the data, the seeded network, and the training loop. Returns JSON that the interface can display.

Frontend

Owns the lesson, controls, charts, and explanations. It never pretends to train; it shows the API’s results.

Shared constants

Feature names, target units, network shape, seed, batch size, and epochs live in one place.

Downloads

The workbook and Python project are the same data and model, prepared for offline study.

Design rules that keep the app honest

  • One source of truth for the seed and the architecture.
  • The backend returns real numbers, not pre-written “nice” results.
  • The UI labels training, validation, and test separately.
  • Every download is generated from the same data contract.
  • Errors are shown to the student instead of hidden.

Build the FastAPI backend

Install the web dependencies in a separate environment or add them to the project:

python -m pip install fastapi uvicorn pandas numpy openpyxl

A minimal API

from fastapi import FastAPI
from pydantic import BaseModel, Field
import numpy as np

app = FastAPI()

class TrainRequest(BaseModel):
    epochs: int = Field(default=10, ge=1, le=30)
    batch_size: int = Field(default=100, ge=10, le=500)
    learning_rate: float = Field(default=0.05, gt=0, le=10)

@app.post("/api/case/exam/train")
def train(request: TrainRequest):
    # Load the workbook, select the splits, scale, and run the
    # same 10-batch NumPy loop from sections 4–6.
    # Return JSON with metrics, batch losses, and predictions.
    return {"epochs": request.epochs, "updates": 100}

Build the browser interface

Use Vite with React, or plain HTML if you are starting smaller. The interface has four jobs:

  1. Explain the problem and the data without hiding the target.
  2. Let the student choose a case, settings, and a step.
  3. Show the real run — losses, metrics, and predictions from the API.
  4. Offer downloads — the workbook, Python project, and this guide.

Add the interactive lesson

The lesson is not a separate product from the model. Each step should point at a number the student can see in the lab.

Make the data tangible

Show the first rows, the split, and the batch number. Let the student hover or click a row.

Make the shape visible

Draw 2 → 3 → 1. Label 9 weights and 4 biases. Do not draw a generic deep network.

Make the update visible

Animate or list batch 1 → batch 2 → … and show that the weights carry forward.

Make the honesty visible

Keep validation and test separate, and say when the test set is opened.

Accessibility and motion

  • Every control has a visible label and a keyboard path.
  • Charts have a text summary or table.
  • Motion that carries data may continue under reduced-motion preferences; decorative motion stops.
  • Pause stops training and animation; reset returns to seed 42.
Checkpoint 11: A student can explain the batch loop using only the interface.

Deploy and update

A simple production layout keeps the API private and lets nginx serve the built frontend:

Browser
  https://your-domain.example/simulator/
        │
        ├── /simulator/          → built React files
        └── /simulator/api/      → FastAPI on 127.0.0.1:8030

Build the frontend

cd frontend
npm ci
VITE_BASE=/simulator/ npm run build

Run the API as a service

[Service]
WorkingDirectory=/home/student/apps/neuron-lab
ExecStart=/home/student/apps/neuron-lab/.venv/bin/uvicorn \
  backend.main:app --host 127.0.0.1 --port 8030
Restart=always

Update safely

  1. Pull the new code.
  2. Install any new Python packages.
  3. Rebuild the frontend with the same base path.
  4. Restart the API service.
  5. Poll /api/presets/one-neuron until it returns 200.
  6. Check the page, the API, and one download.
Never expose the dev server or a database port publicly. Only nginx should listen on 80/443; the API stays on localhost.

Student challenges and next steps

Change the data

Add a third feature, such as sleep hours. The input layer becomes three nodes; recount the weights and biases.

Change the network

Try 2 → 4 → 1, then 2 → 4 → 4 → 1. Compare validation MAE, not training MAE alone.

Change the batch

Use 50 or 200. What happens to the number of updates and the noise in the loss?

Break it deliberately

Set the learning rate to 10 or remove scaling. Explain the failure with the actual numbers.

Improve the interface

Add a row inspector, a batch scrubber, or a “compare two runs” view.

Write the report

State the question, data, architecture, seed, metrics, limitations, and one honest next step.
